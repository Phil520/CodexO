# 设计说明

## 一、为什么不用现成扩展

原计划按攻略安装 VS Code 扩展 `jefersoonaf.codex-usage-remaining`。经检查本机（macOS 26.5）：

- `/Applications` 下没有 Visual Studio Code / Cursor / Windsurf
- `~/.vscode`、`~/.cursor`、`~/.windsurf`、`~/Library/Application Support/Code` 等配置目录均不存在
- `code` / `cursor` / `windsurf` 命令行入口均不存在

攻略给出的三种安装方式（面板搜索、`ext install`、网页唤起）全部以编辑器为宿主，因此在没有编辑器的机器上无法落地。为一个状态栏指示器安装整套编辑器并不划算，故改为自建原生菜单栏 App。

## 二、扩展的行为审计结论

下载 VSIX 并解包静态审查（v1.0.0）后的结论：

- 代码内**没有任何 http(s) 链接字符串**，无 `eval` / `new Function`，不读取 `auth.json`、钥匙串、`.ssh`，无遥测上报
- 只做两件事：① `child_process.spawn` 拉起本地 `codex app-server --listen stdio://`，走 JSON-RPC 调 `account/rateLimits/read`；② 读 `~/.codex/sessions` 日志
- 与本项目相关的一处更正：该扩展**并非**「只读本地日志」。它的实时路径会经本地 codex CLI 请求 `https://chatgpt.com/backend-api/wham/usage`，失败时才回退到会话日志

本项目的监控 App 走的是**回退路径（本地日志）**，好处是全离线、无网络依赖、启动快。代价是数值随会话日志更新，而非实时拉取官方接口。

## 四、菜单栏图标的绘制

图标是「外圈环 + 内圈月亮」的双层结构，用 `CGContext` 直绘到一个 2x 位图上下文（18pt → 36px），再交给 `NSImage(cgImage:size:)`。

**踩过的坑**：最初用 `NSGraphicsContext(bitmapImageRep:)` 建上下文，并手动 `scaleBy(x: 2, y: 2)`。但该初始化方法本身就会依据 `rep.size` 与像素尺寸的差异自动建立点→像素映射，导致实际放大 4 倍，环形溢出画布、只剩左上角一小段。改为 `CGContext` 直绘后行为完全可控。

### 4.1 外圈：5 小时窗口

进度环自 12 点方向顺时针填充，填充比例即 5 小时窗口剩余量，颜色按阈值取绿 / 橙 / 红。底环固定用中性灰（`calibratedWhite: 0.5, alpha: 0.4`）而非动态语义色，保证在浅色和深色菜单栏下都能看见；剩余归零时没有进度弧，纯灰环看起来像「没数据」，故此时整圈改染警示色。

### 4.2 内圈：每周窗口，七档月相

内圈画成一颗月亮，绘制在进度环之前，半径 `radius − lineWidth/2 − 1.0`，与外圈之间留出约 1pt 的缝隙，避免两个圆形糊在一起。

**为什么从「透明度色阶」换成「月相」**：原来的实心圆用透明度分 10 档编码余量，有两个说不清的问题——

1. **编码方向依赖底色明暗**。越实 = 余量越多，这个读法只在浅色底上成立；放到深色菜单栏上就反转为"越实越贴近背景"，十档几乎糊成一片。这逼得我们为同一支紫维护两支颜色，还踩过"外观变了但图标没重画"的坑。
2. **轮廓不恒定**。实心圆越用越淡，最高档和"几乎归零"在缩小后很难区分。

月相靠**形状**表达余量，一支高饱和度的亮黄在深浅底上都清晰；而且轮廓始终是同一颗圆，只是被照亮的部分多寡不同。两个问题一起消失，那套双外观配色的复杂度整个不用维护了。

档位映射（七档，分界取相邻代表值的中点）：

| 档 | 余量区间      | 代表值  | 月相名 | 明暗界线系数 |
| - | --------- | ---- | --- | ------ |
| 1 | 0 – 20%   | 10%  | 眉月  | +0.780 |
| 2 | 20 – 35%  | 30%  | 蛾眉月 | +0.588 |
| 3 | 35 – 45%  | 40%  | 渐盈月 | +0.309 |
| 4 | 45 – 55%  | 50%  | 上弦月 | 0      |
| 5 | 55 – 70%  | 60%  | 渐凸月 | −0.309 |
| 6 | 70 – 90%  | 80%  | 盈凸月 | −0.809 |
| 7 | 90 – 100% | 100% | 满月  | −1.000 |

七档的名称全部取**上弦（盈）方向**的称谓：亮面在右侧、逐渐变胖，与图标里"月亮从右边开始被点亮"的画法一致（北方上弦月正是右边亮）。

### 4.2.1 月相怎么画：两条边界围出一块亮面

亮面由两条边界围成：

- **外缘永远是右半圆**——从圆心正上方经右端到正下方。这不是天文要求，而是阅读直觉：菜单栏图标没有"哪边是天"的参照，用户记住的是"月亮从右边开始被点亮"。
- **明暗界线是一段椭圆弧**，横向半径 = `r · cos(π × 亮度比例)`。满月时退到左边缘（整颗圆都亮），上弦月时正好穿过圆心（一条直线），新月时贴回右边缘（整颗圆都暗）。

实现上有个绕不过去的限制：**`CGPath` 只能加圆弧，没有椭圆弧**。做法是先在单位圆上造出下半段，再用 `CGMutablePath.addPath(_:transform:)` 压成 `(ratio·r, r)` 的椭圆——而不是靠 `CGContext.saveGState()` + CTM 缩放，因为路径元素是在**加入的那一刻**被当前 CTM  bake 进去的，后续再 `restoreGState()` 时的填充变换时机很容易踩坑。整个亮面路径先在 `CGMutablePath` 上拼好再一次性交给 context，也避免半条路径留在错误坐标系里。

### 4.2.2 物理准确 ≠ 图标可读

按公式，亮度比例 0.1 时亮面最宽处只有 `0.05r`——在 18pt 图标上（内圈半径约 4.7pt）就是 **0.24pt ≈ 0.5 个像素**，等于一根看不见的头发丝。也就是说，"天文正确"的实现会让最低档直接变成"内圈消失了"，比原来的透明度方案还糟。

所以给界线系数加了上限 `moonTerminatorCeiling = 0.78`，把最低档的亮面压到约 `0.22r ≈ 2px`，保有一道看得见的月牙。

**这里要记住的判断顺序：读数工具的第一职责是"能读出来"，"还原天象"排在后面。** 视觉编码允许为了可读性偏离物理真实，只要偏离是单向、可预期、且不影响档位单调性的。

另一处配套决定：**暗面不能省**。先画一整颗中性灰（`calibratedWhite: 0.5, alpha: 0.38`，与外圈底环同色）圆，再在它上面画亮面。这样最细的月牙也还挂在一颗完整的圆上，不会变成一根看不出所以然的细线；而且这支灰在深浅两种底色下都能看出"这里有个圆"。余量 0 时只画暗面不画亮面——是一颗灰月亮，而不是空白。

但**无数据时整颗月亮都不画**（图标与菜单图例一致）。只画暗面等于告诉用户"月亮还在、只是全黑了"，那是"额度用完"的意思，与"没读到数"是两回事——这里要表达的恰恰是后者。

调参入口：`moonLevelValues`（七档代表值）、`moonThresholds`（分界）、`moonTerminatorCeiling`（最细月牙下限）、`moonColor` / `moonDarkColor`（配色）。改完用 `tools/main.swift` 生成对照图核对。

亮面色是从四支候选里选的（暖黄 / 琥珀 / 淡金 / 月白），判据只有一条：**深浅两种菜单栏底色下都要看得清**。最终选琥珀 `#FFB020`——淡金和月白虽然更"像月亮"，但在浅色底上会弱到读不出来，而这是读数工具的第一诉求。对照图 `output/preview/moon_color_candidates.png` 由 `tools/color_picker.swift` 生成，它借用 `IconFactory.icon` 的 `moonColor` 默认参数口子，在同一张图上并排画出四支候选。

### 4.4 菜单栏上的排布：数值在左、图标在右

`button.imagePosition = .imageTrailing`，`button.title = "59% "`。理由是菜单栏控件整体从左往右排，靠右的位置容易被别的图标挤掉；把读数放在最左侧，可以保证它始终是第一个被看到的。

顺带一提，`IconFactory.icon` 保留了一个 `moonColor` 默认参数口子。平时调用不用传，只有配色候选页会传——这类"平时不用、调试要用"的开关留一个默认值参数就够了，不必为它单开一套配置。

### 4.3 菜单里的图例

下拉菜单中「每周窗口」那一行标题左侧画一个 14pt 的月相（`MoonView`），把菜单条目和菜单栏图标上的内圈对应起来；悬浮提示里另有一行「内圈月相：n/7 档 · 上弦月，月亮越圆余量越多」。

`MoonView` 与图标内圈**共用 `MoonShape.draw(in:)` 这一份实现**——不是各画各的。两处绘制路径不同（一处画进图标位图、一处是 `NSView.draw`），但形状逻辑只有一份，所以"图上看到的"和"菜单里解释的"不可能对不上。预览图 `moon_phases.png` 最下一行专门走 `MoonView` 这条路径出图，用来核对两者一致。

原来的 `DotView` 用 CALayer 画圆、并覆写 `viewDidChangeEffectiveAppearance()` 跟随外观换色——换月相后这两处都不再需要（CALayer 做不了"圆被一条椭圆弧切开"的路径，配色也不再依赖外观）。

外观切换的重画机制保留：菜单栏明暗仍计入图标渲染签名，并监听 `AppleInterfaceThemeChangedNotification` 延迟 0.3 秒重画。月相配色本身与外观无关，但底色变了图标却还是上一副模样，观感上会像是"没跟上"，重画成本又极低。

注意外观判定比较的是**归类后的明/暗**而不是外观名的字符串——`Palette.isDark(_:)` 用 `bestMatch(from: [.aqua, .darkAqua])`，因为 NSApp 常报 `Aqua`、菜单栏按钮报 `VibrantLight`，名字不同但同属浅色。

## 五、状态判定

沿用小工具原型的阈值：

| 剩余量       | 颜色 | 无障碍描述 |
| --------- | -- | ----- |
| > 30%     | 绿  | 余量充足  |
| 10% – 30% | 橙  | 余量偏低  |
| ≤ 10%     | 红  | 额度紧张  |

窗口过期（`resets_at` 早于当前时间）时按 100% 处理，与扩展一致。

## 六、性能：为什么必须读尾部

第一版取数的写法是「把每个 .jsonl 整读成 String，再 split 成行，逐行找目标事件」。上线时数据源只有 14 MB，跑得动；四天后涨到 **276 MB（单文件 127.6 MB）**，同一份代码单次取数耗时 **7.99 秒**。

而这个调用发生在**主线程**上，触发频率是「每 60 秒一次」+「每次点开菜单一次」。后果是点图标后界面冻结 8 秒，菜单呈现为一片空白——看起来像渲染 bug，实际是性能 bug。

改法三条：

1. **尾部读取**。用 `FileHandle` 定位到文件末尾，往回读一个预算块（1 MB → 8 MB → 64 MB 逐级放大），按换行切分后丢弃开头那半行（被截断的）。正常情况第一个预算就命中，只读 1 MB。
2. **反向扫描**。`lines.reversed()` 从新往旧找，凑齐 5 小时窗口和每周窗口两条读数立即 `break`，不做全文件遍历。
3. **结果缓存**。以「候选文件数 + 最新文件路径 + 最新文件 mtime」为 key：三者都没变，说明日志没被写过，直接复用上次结果。缓存复用时**必须重算与时间相关的字段**（窗口是否已过期、剩余量），否则会把「刚重置」的状态一直锁死。

效果：**7.99 秒 → 0.024 秒**，缓存命中 0.000 秒。

## 七、取数正确性：为什么不能拿「文件修改时间」当新鲜度

### 7.1 现象

用户报「数据都不准确了」。同一时刻三方对照：

|      | 5 小时窗口   | 每周窗口    | 读数时间        | 来源文件           |
| ---- | -------- | ------- | ----------- | -------------- |
| 应用显示 | **100%** | **33%** | 10-10 11:31 | `2026/10/09/…` |
| 真实值  | **74%**  | **96%** | 10-13 13:58 | `2026/10/13/…` |

两个数都错，而且错得"看起来很合理"——5 小时窗口显示 100%，像是额度刚重置。

### 7.2 成因

Codex 的会话文件**可以被重新追加写入**。当天出现的真实数据形态：

| 文件                                    | mtime                | 尾部最新 `token_count` 事件 |
| ------------------------------------- | -------------------- | --------------------- |
| `2026/10/09/rollout-…16-19-35….jsonl` | **今天 16:04**（刚被追加写入） | 10-10 11:31（三天前）      |
| `2026/10/13/rollout-…08-57-32….jsonl` | 今天 13:58             | **10-13 13:58（最新）**   |

旧实现是「按 mtime 倒序取文件 → 在文件里倒序找 → **凑齐两个窗口立即 `break scan`**」。

于是：`10/09` 那个文件因为刚被追加而排到第一位，它尾部确实能扫到一条三天前的 `token_count`（两个窗口都在），扫描就此收工，**永远不会去看含今日数据的第二个文件**。

而那条三天前的读数又被第 5 节的「窗口已过期 → 按 100% 处理」规则接上：它的 `resets_at` 是 10-10 12:37，早已过期，于是 5 小时窗口显示 **100%**；每周窗口的 `resets_at` 还没到，就直接显示了三天前的 **33%**。

**两个设计各自都没错，串在一起就产出了一个看起来很合理的错数**——这是最难发现的一类 bug。

### 7.3 修法

以**事件自带的 `timestamp`** 为准，而不是文件的 mtime：

1. 逐文件取该文件尾部最新的一条 `primary` / `secondary` 读数，连同它的事件时间戳
2. 跨文件比较，**每个窗口各自保留时间戳最新的那条**（两个窗口独立取值，避免互相牵制）
3. 停止条件改为：两个窗口都已取得读数，且当前文件 `mtime` ≤ 两条读数时间戳中的**较小者**

第 3 条的依据是一条不变量：**一条事件的 `timestamp` 不可能晚于它所在文件的 `mtime`**（时间戳记的是事件生成时刻，mtime 记的是写入时刻，后者必然不早于前者）。因此凡是 mtime 早于"已取得的最新读数"的文件，都不可能含有更新的读数。又因为文件已按 mtime 倒序排好，一旦命中该条件，后面的文件必然也命中，可以直接退出扫描——这条规则同时保证了正确性与效率。

实测：正常数据下扫 1–2 个文件即停，冷读 0.054 秒、缓存命中 0.0002 秒。

### 7.4 让新鲜度可见

错数之所以能存在三个多小时没被发现，是因为界面上**没有任何地方告诉你这个数是什么时候的**。现在补上了：

- 菜单里单列一行「**读数 10月13日 13:58 · 来自 …**」，显示的是日志中那条记录自身的时间，不是我们读取它的时间
- 悬浮提示末行「数据记录于：…」

这样即使将来真的出现"数据陈旧"（例如 Codex 几天没跑），也能一眼看出是数据源本身没更新，而不是工具算错了。

### 7.5 回归测试

`tests/main.swift` 末尾新增一条针对性回归：在 `/tmp` 造一份人造日志目录，先写含"新"读数的文件，**再**写含"旧"读数的文件（后写的 mtime 更新，正是骗到旧实现的那个点），断言取数必须选中**事件更新**的那个文件、结果必须是 74% 而不是 100%。

为此把 `UsageReader.sessionRoot` 从 `let` 改成可写的 `var`，并把根目录并入缓存 key，测试里可以指向人造目录。

### 7.6 第二个坑：尾部读取的字节偏移会切断多字节字符

上一节修完后，用户仍反馈"测不准"。这次不是取数口径的问题，而是**读文件的方式**的问题，且更隐蔽。

**现象**：应用显示的读数停在某个旧快照上不再前进，但日志确实在更新。一手对照数据（2026-10-14）：

|      | 5 小时窗口   | 每周窗口    | 读数时间        | 来源文件                    |
| ---- | -------- | ------- | ----------- | ----------------------- |
| 应用显示 | **100%** | **76%** | 10-14 11:14 | `2026/10/13/…08-57-32…` |
| 真实值  | **90%**  | **75%** | 10-14 16:02 | `2026/10/14/…15-48-01…` |

**成因**：为了保证性能，读数只读文件尾部 1 MB，起点是「文件大小 − 1 MB」这个**字节偏移**。而会话日志里满是中文，一个汉字占 3 字节，这个偏移很容易落在某个汉字的**中间**：

```
              …… 汉字 汉 汉 汉 ……
   字节序列：        E6 B1 89 E6 B1 89 E6 B1 89
                              ↑
                    起点落在这里（续字节 0xB1）
```

旧代码的顺序是「先 `String(data:encoding:.utf8)` 整段解码 → 再在字符串里找第一个换行丢掉半行」。问题在于：**从续字节开始的整段字节流根本不是合法 UTF-8**，`String(data:encoding:.utf8)` 会直接返回 `nil`，根本走不到"找换行"那一步。

而上游的写法是 `guard let lines = tailLines(...) else { break }`——拿到 `nil` 就跳出"1 MB → 8 MB → 64 MB 逐级放大"的循环，**既不重试更大的预算，也不报错**。结果是最新那份会话文件被整份静默跳过，扫描顺延到下一个文件，取到了上一个文件的旧读数。

**为什么表现为"时好时坏"**：文件小于 1 MB 时起点为 0、整份读入，永远不会切坏；只有单个会话文件**长过 1 MB 之后**才会触发。所以症状是"用着用着数字就不动了"，而不是一开始就错——这类"环境状态越过某个阈值后才出现"的 bug，最容易让人怀疑是显示或取数逻辑，而不是文件读取本身。

**真实证据**：最新文件 1,322,179 字节，1 MB 尾部起点偏移 273,603，该处首字节 `0xAD`（`0x80`–`0xBF` 区间，标准续字节），整段解码报 `invalid start byte`；而 8 MB 预算下起点为 0，解码正常——但代码没走到那一步。按中文为主的日志算，该偏移落在续字节上的概率是 **2/3**。

**修法**（两层）：

1. **切行放到字节层面**：先 `data.firstIndex(of: 0x0A)` 找到第一个换行，按字节切掉前半行，**再**解码。这样解码的输入必然从行首开始，永远是合法 UTF-8。
2. **有损解码兜底**：用 `String(decoding:as:UTF8.self)` 代替 `String(data:encoding:.utf8)`。它不会失败，非法字节变成替换字符，最多让那一行的 JSON 解析失败被跳过——不会把整份文件丢掉。

这条修改同时消掉了「读取失败会被静默当成没有数据」这个更危险的设计：任何时候都不该让"读不出来"和"没有数据"变成同一种表现。

**回归测试**：`tests/main.swift` 造一个 1.5 MB 的会话文件，用 3 字节汉字填充，**主动把「文件尾 − 1 MB」这个偏移调整到汉字中间**（先判断 `boundary % 3`，必要时补一个 2 字节字符把偏移挪进续字节区），再放一个读数不同的对照文件。

测试本身有个易错点值得记：算偏移时要按**最终文件内容**算，别忘了填充区与 JSON 行之间那个 1 字节的换行——漏掉它就会刚好差 1 字节，把边界挪回字符起始位置，测试表面上通过、实际什么都没验证。第一版就是栽在这里，先用旧实现跑了一遍发现"也能通过"才发现的。

修好之后，这条测试在旧实现上**失败**（读成对照文件的 15%），在修复版上**通过**（读到 90%），与线上真值一致。

## 八、长期运行的内存纪律

这是个常驻一两周不下线的程序，「跑几天内存涨上去」比「一次调用慢」更致命——慢能感知到，涨是悄悄发生的，等发现时进程已经吃掉几百 MB。所以本次专门建了一套可在几分钟内验证「跑几天会怎样」的手段。

### 8.1 手段：把「跑几天」压缩成「跑几分钟」

两条并行的验证路径：

**其一，进程内压测。** 把定时刷新、重画图标、更新菜单三条路径各抽成一个闭包，循环调用成千上万遍，每 250 遍用 `task_info(TASK_VM_INFO)` 读一次 `phys_footprint`（即活动监视器「内存」列的口径）并打点。因为菜单相关的 AppKit 对象需要真实进程才有意义，压测是**做在 App 内部**的，由环境变量 `CODEX_USAGE_SOAK` 触发，跑完可自动退出。


**其二，真实进程加速跑。** 用 `CODEX_USAGE_REFRESH` 把刷新间隔从 60 秒改成 0.02 秒（50 次/秒），配 `CODEX_USAGE_MEMORY_INTERVAL=5` 每 5 秒记一次内存，3 分钟即等效于约 6 天的触发量。这条路径走的是**真 RunLoop、真 NSStatusItem、真定时器**，补上了压测的合成环境所缺的部分。

### 8.2 关键方法论：先分离「真泄漏」和「自动释放池堆积」

第一轮压测给出的是：重画图标 4000 次 **+30.5 MB**（约 8 KB/次，恰好等于一张 36×36 位图的大小），打开菜单（旧写法）4000 次 **+197 MB**。看着像是两个确凿的位图泄漏。

但这个结论**是错的**——那一轮所有循环都跑在**没有自动释放池**的环境里（命令行进程，没有 RunLoop 帮忙收池）。给每轮循环套上 `autoreleasepool {}` 后重测：

| 路径 | 不收池 | 收池（= 真实 App 的环境） |
|------|--------|--------------------------|
| 定时刷新 | +0.02 MB | +0.02 MB |
| 重画图标 | **+30.5 MB** | **±0 B** ← 假象 |
| 打开菜单·现写法 | +0.02 MB | ±0 B |
| 打开菜单·旧写法 | +197 MB | **+4.84 MB** ← 真泄漏 |

只有**旧菜单写法**在收池后依然单调上涨（常驻内存每 250 次稳定 +0.4 MB，4000 次共 +6.89 MB，曲线严格线性），才是真泄漏；图标的「8 KB/次」完全是自动释放对象没被回收的假象。

**这条经验比结论本身更重要**：在非 RunLoop 环境里测内存，任何「每次循环增长几 KB」都先别急着下结论，一定要加一个「收池 / 不收池」的对照。否则会把自动释放堆积当成泄漏去改代码，改错地方。

### 8.3 三条修复

1. **菜单只建一次。** 旧写法每次开菜单 `removeAllItems()` + 重建两个 `UsageItemView`，会稳定泄漏约 1.3 KB/次。改为启动时把所有菜单项与视图建好，开菜单只调 `UsageItemView.update(window:emptyText:)` 改文字与进度条、只改 note 项的 `attributedTitle`。4000 次实测从 +4.84 MB 变为 ±0 B。
2. **图标签名缓存。** 用「5H 剩余取整 + 周剩余取整」拼一个签名，签名未变就复用上一张 `NSImage`，省掉新建 `CGContext` + 位图 + `NSImage`。
3. **热点回调显式收池。** 定时器回调、菜单更新、`UsageReader.load()` 内部都包了 `autoreleasepool {}`，不依赖上层环境。

附带修掉的两处浪费：`DateFormatter` / `ISO8601DateFormatter` 由每次调用新建改为静态复用（它们是重对象）；诊断日志超过 512 KB 自动滚动，不会无限增长。

### 8.4 结果

- 空载占用约 **12–13 MB**
- 真实进程加速跑 3 分钟（≈6.25 天触发量）：内存 **15.4 MB → 12.9 MB 后一直持平**，常驻内存从 49.6 MB 缓降到 38.4 MB
- 菜单里直接显示当前内存与已运行时长，随时可自查

### 8.5 顺手抓出的一个 bug

`static let launchedAt = Date()` 用来算运行时长时，菜单里显示成了「运行 已重置」。原因是 **Swift 的静态属性是懒加载**，`launchedAt` 直到第一次被读取才初始化，于是「运行时长」从第一次读取那一刻算起，差值为 0，而 `humanize()` 对 ≤0 的间隔返回「已重置」（它本来是给重置倒计时用的）。改为在 `applicationDidFinishLaunching` 开头显式调用 `markLaunch()` 赋值，并把「时长描述」与「倒计时描述」拆成 `Format.duration` 与 `Format.humanize` 两个函数。

## 九、已知限制

1. 数值更新滞后于实际消耗，取决于 Codex 何时把新的 `token_count` 事件写进会话日志
2. 未实现官方实时接口（那条路径需要拉起 `codex app-server` 子进程，且依赖网络可达 `chatgpt.com`）
3. 开机自启动通过 `~/Library/LaunchAgents/com.bean.codex-usage-menubar.plist` 实现，可在菜单里开关
4. 内圈月相的最低档（周余量 <20%）是一道约 `0.22r` 宽的月牙，正常距离看偏细。这是「余量越少月亮越瘦」的必然结果，已用暗面圆托底保证轮廓完整；必要时可调 `moonTerminatorCeiling`（如 0.72 会更粗）
5. 本机未授予屏幕录制权限，菜单栏实际观感无法截图核对，只能靠 `tools/` 生成预览图目视确认
6. 压测的 `menu-rebuild` 模式只在「不进菜单窗口」的合成环境里测过，真实弹出菜单时视图会带图层背衬，实际每次泄漏量应大于 1.3 KB——但方向与结论不变
7. 七档月相的界线系数是按公式算的，只有最低一档（眉月）因为可读性做了 clamp，其余六档未做逐档目视调校。若觉得 40% 与 50% 两档在小图标上分不开，需要重新挑选代表值而不是改系数
