## v1.0.0

原标题：CodexO v1.0.0

```markdown
## CodexO 1.0.0

macOS 菜单栏小工具，实时显示 Codex 的**剩余额度**。

<img src="https://github.com/Phil520/CodexO/raw/main/docs/screenshot.png" width="720" alt="七档月相">

菜单栏上一颗双层圆标：

- **外圈** —— 5 小时窗口的剩余进度环，绿 / 橙 / 红随余量变色
- **内圈** —— 每周窗口的**月相**，七档：月亮越圆，余量越多

从左到右是「**数字 + 图标**」，数字即 5 小时窗口的剩余百分比。

### 下载

**CodexO-1.0.0.zip**（308 KB）—— 解压得到 `CodexO.app`，拖进「应用程序」即可。

> **首次启动可能被 Gatekeeper 拦一下。** 因为没有 Apple 开发者证书做公证，
> 右键点 `CodexO.app` → **打开** → 再点「打开」。这是一次性的，之后正常双击就行。

### 环境要求

- macOS 13 或更高
- 机器上装好并且**实际用过** Codex（需要 `~/.codex/sessions` 里有会话日志）

> **若菜单栏看不见图标：先退出 Hidden Bar。** 实测只要 Hidden Bar 在跑，
> 任何新建的菜单栏项都会被 macOS 排到屏幕外。这与 CodexO 无关，
> 一个 10 行的最小程序同样会被挤出去。

### 特点

- **只读、不联网** —— 只读本机 `~/.codex/sessions`，不上传任何数据，不发任何网络请求
- **原生** —— Swift + AppKit，无 Xcode 工程，无第三方依赖
- **常驻稳定** —— 空载约 12 MB 内存，4000 次压测与 6 天加速实跑均无泄漏
- **能看见数据的年龄** —— 菜单里直接显示读数时间与「多少分钟前」

### ⚠️ 一个必须说清楚的限制

**CodexO 显示的是「最近一次 Codex 请求时」的读数，不是实时读数。**

Codex 官方 App 自己直接查服务端，而 CodexO 读的是本地日志里最近一次落盘的快照：

- **持续用 Codex 时** —— 每个请求都刷新日志，两边基本一致
- **停手之后** —— 官方 App 继续跟着服务端走，CodexO 冻在最后一次的值上

所以「数字不动」通常不是坏了，而是**这段时间没有新的请求**。
菜单里那行「读数 14:32（38 分钟前）」就是给这件事看的。

### 自行编译

```bash
git clone https://github.com/Phil520/CodexO.git
cd CodexO
bash build.sh
open output/CodexO.app
```

只需要 Xcode 命令行工具。

## v1.0.1

原标题：CodexO v1.0.1

```markdown
## CodexO 1.0.1

修一个让人生气的问题：**手动点「立即刷新」，读数不跟着变。**

### 现象

新建一个 Codex 会话，然后点菜单里的「立即刷新」，看到的还是很久以前的
读数（5 小时窗口显示 100%，真实值 98%）。从用户角度看就是
「我明明点了，它就是不动」。

### 原因

不是没刷新，而是**「刷新」这个动作被缓存挡住了**。

读数有缓存，key 只看「修改时间最新的那个文件」的 mtime。问题在于
Codex 刚新建会话时，那个文件里**还没有写入任何额度数据**——
会话刚创建，额度要等第一次请求之后才落盘。于是点刷新时算出来的 key
和上一次完全相同 → 缓存命中 → 直接返回旧结果。

实测时序（2026-10-19）：

```
10:49:04  用户点「立即刷新」      ← 这一刻客观上确实还读不到新数据
10:49:47  新会话才写出第一条额度数据
10:50:39  App 自己刷新时读到了 98%
```

### 修法

给取数器加一个「清缓存」入口，「立即刷新」先清缓存再取数。

自动刷新仍然信任缓存（省掉重扫），但**手动刷新一定真的重扫**。

### 这类事的通用教训

**凡是有缓存的地方，就必须有一条能让用户主动绕过它的路径。**

用户点刷新，意思是「我怀疑你算错了，去看看」。这时候拿缓存糊弄他，
就是**把用户的质疑当成噪声**——这是最让人恼火的失败方式：
用户知道该怎么做、也照做了，但工具把那个动作静默吞掉。

### 升级

直接下载下面的 zip 覆盖即可（保持同一个 App，跑起来还是菜单栏里那个）。

如果之前是从 GitHub Releases 下的 1.0.0，用这个替换它。
```

## v1.0.2

原标题：CodexO v1.0.2

```markdown
## CodexO 1.0.2

修两件事，都跟我发布时的验收疏漏有关。

### 一、菜单栏出现两个图标（你在 1.0.1 上遇到的）

**原因在我，不在软件。** 验收时我从临时目录启动了一个副本做验证，
看完就删目录 —— **但没先停进程**。macOS 里已加载的程序不会因为可执行文件
被删就自动退出，于是那个进程成了孤儿，继续挂在菜单栏上。

这事的危害不只是"多一个图标"：

- 孤儿进程一直吃一份内存，你不知道它从哪来；
- **两个进程写同一个日志文件**，行与行交错 —— 那份日志直接作废，
  而"日志不可信"是排查里最致命的前提失效；
- 你看到两个图标会以为软件不稳定。

### 二、现在加了单实例保护

启动时抢一个含 pid 的锁文件，已经有实例在跑就直接退出。

为什么不给"注意别开两个"这种提示就完事：

- 多开一个是很自然的行为，指望人人先看菜单栏不现实；
- 开发者和脚本作者也常常会忘（包括我）；
- **单实例对这个 App 是产品要求，不是可选项** —— 两个图标会让人
  以为它不稳定，而两个进程混写日志会让排查失效。

锁文件里记着 pid。进程被强杀（崩溃 / `pkill -9`）会留下锁，
所以下次启动会先看 pid 还在不在，不在就回收。
少了这一步，用户强杀一次之后就再也起不来 —— 那比两个图标更糟。

### 三、日志每行都带 pid

```bash
grep '刷新' ~/Library/Logs/CodexUsageMenuBar.log | awk '{print $3}' | sort | uniq -c
```

正常只有一个数字。出现两个，说明有多个实例在写同一份日志。

**共享的日志没有署名，等于没有日志。**

### 升级

下载下面的 zip 覆盖即可。

如果你用的是 1.0.1 或 1.0.0，不需要手动清理什么 ——
那个孤儿进程在你的机器上已经关掉了。
```

## v1.0.3

原标题：CodexO 1.0.3

```markdown
修复单实例保护的一个漏洞：副本退出时会误删正式实例的锁，导致第三个进程畅通无阻——菜单栏再次出现两个图标。

## 根因

`applicationWillTerminate` 无条件删锁文件。副本被单实例检查拦下后会走 `NSApp.terminate`，于是它照样把正式实例持有的锁一起删了。

1.0.2 的修复只挡住了一半：能挡住第二个进程，但挡不住「第二个进程把门闩抽走之后进来的第三个」。

## 修法

只删「锁文件里写的是自己 pid」的那把锁。判归属不靠内存标志位，而是回头读锁文件对账，副本与僵尸实例都自动安全。

## 顺带修正一个认知

LaunchServices 会按 bundle id 拦下重复 `open`，同一个 App 连点三遍根本不会起第二个进程。单实例锁真正要挡的是**不同路径的副本**——上次的两个图标正是 /tmp 下的测试副本造成的。以后验收只测「重复 open」测不出问题。

## 验证

新增回归测试 `tests/single_instance.swift`：起真实子进程，A 持锁 → 副本 B 被拦 → 判锁是否还在 → 副本 C 是否也被拦。已先用修复前的实现跑过一遍确认会失败（精准失败在「副本 B 把 A 的锁误删了」，其余判据全过）。

回归测试已挂进 `build.sh`，`bash build.sh` 一次跑完构建 + 四条回归。

## 验证结果

- 月相几何：七档面积 10.96% → 99.98%，与理论值偏差 ≤0.04 个百分点
- 取数：三条回归全过
- 单实例：六条判据全过
- `gh release download` 拉回来重新跑过一遍
```
