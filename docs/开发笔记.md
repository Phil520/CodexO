# project028_Codex用量菜单栏

## 项目简介

macOS 菜单栏小工具，实时显示 Codex 在当前 5 小时窗口与每周窗口的剩余额度。菜单栏上是一个双层图标：**外圈**是 5 小时窗口的环形进度，**内圈**是每周窗口的圆（透明度分 10 档，颜色跟随菜单栏明暗自动切换）。点开可看详细数据与重置倒计时。

本项目的起因：原本打算安装 VS Code 扩展 `jefersoonaf.codex-usage-remaining`，但本机没有安装任何 VS Code / Cursor / Windsurf，扩展无处可装。于是改为直接用 Swift 写一个原生菜单栏 App，取数口径与该扩展完全一致，但不依赖任何编辑器。

## 取数口径

与扩展 `jefersoonaf.codex-usage-remaining` 保持一致，**只读本地文件，不联网**：

1. 扫描 `~/.codex/sessions/**/*.jsonl`，只取最近 7 天内修改过的文件
2. 每个文件**只读尾部**（1 MB → 8 MB → 64 MB 逐级放大），倒序找到该文件里最新的一条 `token_count` 事件
3. **跨文件比较，取事件时间戳真正最新的那条**——不是取"文件修改时间最新"的那个文件的读数
4. `rate_limits.primary` → 5 小时窗口；`rate_limits.secondary` → 每周窗口（两者各自独立取最新）
5. 剩余百分比 = 100 − `used_percent`；若 `resets_at` 已过期则显示 100%（窗口已重置）

阈值沿用扩展默认值：剩余 ≤ 30% 转黄，≤ 10% 转红。

### ⚠️ 为什么必须按「事件时间戳」而不是「文件修改时间」取数

这里踩过一个代价不小的坑，值得单独记一笔。

Codex 的会话文件是**可被重新追加写入**的：一个 10 月 9 日创建的会话，到了 10 月 13 日仍可能被写进几行。于是会出现这种数据形态——

| 文件 | mtime | 尾部最新事件 |
|------|-------|-------------|
| `2026/10/09/…jsonl` | **今天 16:04**（刚被追加） | 10-10 11:31（三天前） |
| `2026/10/13/…jsonl` | 今天 13:58 | **10-13 13:58（最新）** |

按 mtime 排序时第一个文件是 `10/09` 那个，而它**尾部最新的事件是三天前的**。旧实现只要在某个文件里凑齐了两个窗口就立即 `break scan`，于是拿这份三天前的快照当成了当前值：5 小时窗口因为旧读数已过期被判成 **100%**，每周窗口显示成 **33%**（真值是 74% / 96%）——两个数全错，而且看起来还挺"合理"。

修法：**以事件自带的 `timestamp` 为准跨文件比较**，每个窗口各自取时间戳最新的那条读数。停止扫描的条件也跟着改：

> 当两个窗口都已取得读数，且当前文件的 `mtime` **不晚于**这两条读数时间戳中的较小者时，就可以停止——因为一条事件的 `timestamp` 不可能晚于它所在文件的 `mtime`，比它更旧的文件里不可能有更新的读数。

因为文件已按 mtime 倒序排列，一旦命中这个条件，后面所有文件也必然满足，可以直接退出。实测这条规则在正常数据下只需扫 1–2 个文件；冷读 0.054 秒、缓存命中 0.0002 秒。

菜单里专门显示了一行 **「读数 10月13日 13:58 · 来自 …」**，显示的是日志里那条记录自身的时间（不是我们读它的时间），一眼就能判断数据新不新鲜。悬浮提示里也有一行「数据记录于」。

`tests/main.swift` 里有一条对应的回归测试：人造一份"旧文件被重新追加"的日志目录，断言取数必须选中事件更新的那个文件。

### ⚠️ 尾部读取必须在**字节层面**切行，不能先整段解码

第二个取数坑，比上一个更隐蔽，也是"数字用着用着就不动了"的真正原因。

**成因**：尾部读取的起点是「文件大小 − 1 MB」这个**字节偏移**。会话日志里满是中文（工具输出、思考内容），一个汉字占 3 字节，这个偏移完全可能落在某个汉字的**中间**：

```
              …… 汉字 汉 汉 汉 ……
   字节序列：        E6 B1 89 E6 B1 89 E6 B1 89
                              ↑
                    起点落在这里（续字节 0xB1）
```

从续字节开始解码，整段 bytes 就不是合法 UTF-8，`String(data:encoding:.utf8)` **直接返回 `nil`**；旧代码把这个 `nil` 当成"这个文件没读头"，跳出放大预算的循环，**于是最新那份会话文件被整份静默跳过**，界面显示的是上一个文件的旧读数。

**为什么表现为"时好时坏"**：文件不到 1 MB 时起点为 0、整份都读，永远不会切坏；只有单个会话文件**长过 1 MB 之后**才会触发。所以症状是"用着用着数字就不动了"，而不是一开始就错。按中文为主的日志算，这个偏移落在续字节上的概率是 2/3。

**修法**：切行放在**字节层面**做——先按字节找到第一个换行（`0x0A`）再解码，绝不先整段解码、再去字符串里找换行；同时用 `String(decoding:as:UTF8.self)` 有损解码兜底，万一日志正写到一半，也只是那一行 JSON 解析失败被跳过，不会把整份文件丢掉。

**真实证据**（2026-10-14 的一手数据）：最新会话文件 1,322,179 字节，1 MB 尾部起点偏移 273,603，该处首字节 `0xAD` 正是续字节；整段 UTF-8 解码失败，最新文件被跳过，界面显示成上一个文件的 `100% / 76%`，真值是 `90% / 75%`。

`tests/main.swift` 里补了对应回归：造一个 1.5 MB 的会话文件，**主动把「文件尾 − 1 MB」这个偏移调到汉字中间**，再放一个读数不同的对照文件，断言必须取到大文件的读数。这条测试在旧实现上**会失败**（读成对照文件的 15%），修复后通过。

### 菜单栏图标：外圈看 5 小时，内圈看每周

菜单栏上从左到右是 **`59%` + 月亮图标**：数值在左、图标在右。菜单栏控件整体从左往右排，靠右的位置容易被别的图标挤掉，把读数放在最左侧可以保证它始终第一个被看到。

一个 18pt 的小图标里放两路信息：

| 位置 | 含义 | 编码方式 |
|------|------|----------|
| 外圈环 | 5 小时窗口剩余量 | 进度弧填充比例，颜色按阈值取绿 / 橙 / 红（≤30% 橙，≤10% 红） |
| 内圈月亮 | 每周窗口剩余量 | **月相**：满月 = 余量充足，弯月 = 快用完了。亮面 `#FFB020`（琥珀），暗面中性灰 |

### 内圈月相：七档，10 / 30 / 40 / 50 / 60 / 80 / 100

余量落到七档之一，每档对应一个月相名。档位分界取相邻代表值的中点：

| 档 | 余量区间 | 代表值 | 月相 | 明暗界线系数 |
|---|---|---|---|---|
| 1 | 0 – 20% | 10% | 眉月 | +0.780 |
| 2 | 20 – 35% | 30% | 蛾眉月 | +0.588 |
| 3 | 35 – 45% | 40% | 渐盈月 | +0.309 |
| 4 | 45 – 55% | 50% | 上弦月 | 0（正中间一条直线） |
| 5 | 55 – 70% | 60% | 渐凸月 | −0.309 |
| 6 | 70 – 90% | 80% | 盈凸月 | −0.809 |
| 7 | 90 – 100% | 100% | 满月 | −1.000 |

**画法**：一颗完整的暗面圆，加一块被照亮的区域。亮面由两条边界围成——右半圆（亮的永远是右边，符合"月亮从右边开始被点亮"的直觉，北方上弦月也正是右边亮），以及一段椭圆弧，也就是明暗交界线。

交界线的横向半径 = `r · cos(π × 亮度比例)`：满月时退到左边缘（整颗圆都亮），上弦月时正好穿过圆心（一条直线），新月时贴回右边缘（整颗圆都暗）。这是天文上准确的算法。

**但物理准确 ≠ 图标可读**，所以给系数加了上限 `0.78`：亮度比例 0.1 时，按公式算出来的亮面最宽处只有 `0.05r`，在 18pt 的菜单栏图标上就是一根看不见的头发丝。压到 `0.78` 之后最低档仍保有一道约 `0.22r` 宽的月牙。**读数工具的第一职责是"能读出来"，不是"还原天象"。**

暗面不能省。留着它，最细的月牙也还挂在一颗完整的圆上，不会变成一根看不出所以然的细线；而且中性灰在深浅两种菜单栏底色下都能看出"这里有个圆"。暗面用的是 `50% 灰 α38%`，与外圈底环同一支色。

亮面色是从四支候选里选的，判据只有一条：**深浅两种底色下都要看得清**。

| 候选 | 色值 | 结论 |
|---|---|---|
| A 暖黄 | `#FFD24A` | 合格，但偏"塑料黄" |
| **B 琥珀** | **`#FFB020`** | **选中**。橙调更"有光"，深浅底色下都醒目 |
| C 淡金 | `#F7E7A6` | 最接近真实月色，但浅色底上明显偏弱，低档月牙看不出来 |
| D 月白 | `#DCE6F5` | 深色底上很干净，浅色底上基本消失，排除 |

对照图见 `output/preview/moon_color_candidates.png`，四支候选各在浅色 / 深色底上画了一条真实 18pt。生成方式：


### 为什么换掉原来的透明度编码

原来是"实心圆 + 透明度分 10 档"，换掉有两个实际好处：

1. **不再依赖底色明暗。** 透明度编码只在浅色底上成立——越实越显眼；放到深色菜单栏上方向会反过来（越实越暗、越贴近背景），所以过去不得不维护两支深浅不同的紫色（浅色 `#4A3A7C` / 深色 `#9889C8`）。月相靠**形状**表达余量，一支高饱和度的亮黄在深浅底上都清晰，一支颜色就够，那套双外观配色的复杂度整个消失了。
2. **轮廓恒定。** 原来的实心圆越用越淡，最高档和"几乎归零"在缩小后很像；月相始终是同一颗圆，只是被照亮的部分多寡不同。

系统在浅色 / 深色之间切换时仍会立即重画图标（监听 `AppleInterfaceThemeChangedNotification`，延迟 0.3 秒避开外观未落定的瞬间），不必等下一次 60 秒刷新——重画成本可忽略，但能避免"菜单栏底色变了、图标还是上一副模样"的观感问题。诊断日志里有两行可直接核对：

```
外观       : 深色（darkAqua） · NSApp=NSAppearanceNameDarkAqua · button=NSAppearanceNameVibrantDark
内圈月相   : #FFB020 亮面 · 暗面中性灰 50% α38%（深浅外观通用）
当前月相   : 5/7 档 · 渐凸月
```

注意外观判定比较的是**归类后的明/暗**，不是外观名的字符串：NSApp 常报 `Aqua`，而菜单栏按钮报 `VibrantLight`，名字不同但同属浅色。比字符串会天天误报"不一致"。

换算代码在 `Palette.moonPhase(forRemaining:)`，绘制在 `MoonShape.draw(in:)`——菜单栏图标内圈和菜单里的图例共用这一份实现，保证"图上看到的"和"菜单里解释的"永远是同一个形状。

- 余量恰好为 0 时落在第 1 档（最细的月牙），而不是不画——这样仍能看出「月亮还在，只是快用完了」
- 每周窗口无数据时**整颗月亮都不画**（不是只画暗面）。只画暗面等于说"月亮还在、只是全黑了"，那是"额度用完"的意思，与"没读到数"是两回事
- 档位只会随余量增加而变亮，不会来回跳

想调手感改 `src/MenuBarUI.swift`：`moonLevelValues` 是七档的代表值，`moonThresholds` 是分界，`moonTerminatorCeiling` 控制最细月牙的下限，调亮/调暗换 `moonColor`。

### 性能设计（重要）

会话日志是持续增长的，**单个文件可达上百 MB**。取数实现因此有三条硬约束：

- **只读尾部**：按 1 MB → 8 MB → 64 MB 逐级放大读取预算，命中即停，正常只读 1 MB
- **反向扫描**：从文件末尾往开头找，凑齐两个窗口立即返回，不遍历全文件
- **结果缓存**：以「候选文件数 + 最新文件路径 + 最新文件 mtime」为 key；三者都没变说明日志没写过新东西，直接复用（0.000 秒），并重算与时间相关的字段

实测：会话日志涨到 276 MB 时，整读实现单次耗时 7.99 秒（会把主线程冻住），尾部读取实现 **0.024 秒**。

## 资源占用与长期运行（重要）

这是一个常驻一两周不下线的菜单栏程序，所以「跑几天会不会把内存吃掉」是硬指标。

**当前空载占用约 12–13 MB**（物理内存口径，即活动监视器里显示的那个数）。菜单第一屏的那行小字里直接写着当前内存与已运行时长，随时可以自己看。

### 三条纪律

1. **菜单只建一次，之后只更新内容。** 早先的写法是每次打开菜单都 `removeAllItems()` 再新建两个自定义视图。实测这是**真泄漏**：即使每轮都收自动释放池，仍然稳定以约 1.3 KB/次的速率单调上涨；而真正把菜单显示出来时，视图还会带上图层背衬（320×62 在 Retina 下约 300 KB/个），实际代价更大。改成启动时建一次、开菜单只改文字与进度条后，4000 次实测**零增长**。
2. **图标只在「渲染输入真的变了」时重建。** 用「5H 剩余 + 周剩余」拼一个签名，签名没变就复用上一张 `NSImage`，省掉每次新建 `CGContext` + 位图 + `NSImage`。
3. **热点回调显式收池。** 定时刷新、菜单更新、取数解析都包在 `autoreleasepool {}` 里，不指望上层环境帮忙收。

另外日志文件超过 512 KB 会自动滚动成 `.log.1`（只保留一份），避免长期运行把日志撑大。

### 自己验证的方法

内置了三个环境变量开关，可以把「跑几天」压缩成「跑几分钟」：

```bash
# 压测模式：把刷新/重画图标/更新菜单各跑 N 遍，每 250 遍记一次内存，跑完即退
CODEX_USAGE_SOAK=4000 CODEX_USAGE_SOAK_MODE=all CODEX_USAGE_SOAK_EXIT=1 \
  ./output/CodexUsage.app/Contents/MacOS/CodexUsageMenuBar

# 真实进程加速跑：0.02 秒触发一次 + 每次强制重画图标，每 5 秒记录内存
CODEX_USAGE_REFRESH=0.02 CODEX_USAGE_SOAK_FORCE_ICON=1 CODEX_USAGE_MEMORY_INTERVAL=5 \
  ./output/CodexUsage.app/Contents/MacOS/CodexUsageMenuBar
```

| 变量 | 作用 |
|------|------|
| `CODEX_USAGE_SOAK` | 迭代次数，设置后才启用压测 |
| `CODEX_USAGE_SOAK_MODE` | `timer` / `icon` / `menu` / `menu-rebuild` / `all` |
| `CODEX_USAGE_SOAK_POOL=0` | 关闭「每轮一个自动释放池」，用于区分真泄漏与自动释放对象堆积 |
| `CODEX_USAGE_SOAK_EXIT` | 压测跑完直接退出，便于脚本化 |
| `CODEX_USAGE_REFRESH` | 覆盖刷新间隔（秒），用于加速真实进程 |
| `CODEX_USAGE_SOAK_FORCE_ICON` | 每次定时回调都强制重画图标（模拟数值持续变化的最坏情况） |
| `CODEX_USAGE_MEMORY_INTERVAL` | 覆盖内存自检写入间隔（秒） |

`menu-rebuild` 模式复刻的是改造前的写法，**专门留着做对照**：同样的环境、同样的迭代数，一个涨一个不涨，比任何解释都直观。

### 实测结论

| 路径 | 4000 次后的净变化 | 结论 |
|------|------------------|------|
| 定时刷新（`timer`） | +0.02 MB | 无泄漏 |
| 强制重画图标（`icon`） | ±0 B | 无泄漏 |
| 打开菜单·现写法（`menu`） | ±0 B | 无泄漏 |
| 打开菜单·旧写法（`menu-rebuild`） | **+4.84 MB** | 真泄漏，约 1.3 KB/次 |

真实进程加速跑（0.02 秒/次，连跑 3 分钟 ≈ **9000 次刷新 + 9000 次重画 ≈ 正常运行 6.25 天**）：
内存从 15.4 MB 落到 12.9 MB 后**一直平在 12.9 MB**，常驻内存还从 49.6 MB 缓降到 38.4 MB，全程无上升趋势。

## ⚠️ 重要前置条件：先关掉 Hidden Bar

本机排查发现：**只要 `Hidden Bar` 在运行，任何新建的菜单栏状态项都会被 macOS 排到屏幕外**（`x ≈ -4100`，而显示器最左只到 `-1470`），图标完全不可见。这与本 App 的代码无关——一个 10 行的最小状态项程序同样会被挤出屏幕。

- 排障时已退出 `Hidden Bar`，图标随即正常出现在外接屏菜单栏右侧
- 如果图标又不见了，**先退出 Hidden Bar** 再看
- 同类工具（Bartender / Ice / Dozer 等）都建议先排除

## 备注

- 前提是机器上已经装好并能正常使用 Codex，且 `~/.codex/sessions` 有会话日志；否则菜单栏显示 `--`。
- 额度耗尽时 Codex 会写入 `primary` / `secondary` 为 `null` 的事件，本工具按窗口各自回溯到最近一条有效读数，不会因此显示为空。
- 诊断日志：`~/Library/Logs/CodexUsageMenuBar.log`（启动自动写两份，菜单里也可手动触发）。
- 数据刷新依赖会话日志写入，所以只有在 Codex 实际跑过之后数值才会更新，自动刷新间隔 60 秒。
- App 为 `LSUIElement`（不显示 Dock 图标），仅存在于菜单栏。
- 本机未授予屏幕录制权限，故菜单栏图标的显示效果需人工目视确认。
